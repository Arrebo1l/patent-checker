# 结项汇报材料

## PPT 大纲(9 页)

### 第 1 页 · 背景与问题
- 场景:手里有一个专利,想知道市面上哪些公司的哪些产品可能侵权
- 痛点:人工逐个读专利权利要求、对照产品说明,慢且难以规模化
- 目标:做初筛,把几十个产品缩小到最值得人工细看的两三个

### 第 2 页 · 演示截图:输入与加载
- 表单输入专利号与公司名
- 加载状态提示(首次分析约 60 秒,内部 11 次 LLM 调用)

### 第 3 页 · 演示截图:结果卡片
- 顶部整体风险评估
- 每个产品一张卡片:风险徽章、命中的权利要求、匹配特征、判定理由

### 第 4 页 · 演示截图:错误处理与历史报告
- 不存在的专利 → 红色错误条显示具体原因
- 历史报告列表、保存与导出 JSON

### 第 5 页 · 系统架构
- React (Vite) → FastAPI → LangChain (Gemini) → 本地 JSON
- 分析流水线六步:查数据 → 定位独立 claim → 提取特征 → 逐个产品打分 → 排序取 Top 2 → 生成整体评估
- 后端按职责拆成六个模块

### 第 6 页 · 难点一:区分"无匹配"与"系统故障"
- 问题:失败调用被记为 0 分,服务全挂时与"产品确实无关"无法区分
- 解决:失败调用不进结果集,空结果集成为"全部失败"的可靠信号
- 效果:503 判断准确,真实的 0 分结果不再被误判

### 第 7 页 · 难点二:跨语言公司名 + 性能
- 问题一:用户输入"沃尔玛",数据里是 "Walmart Inc.",模糊匹配无能为力
  - 解决:在 agent 与数据层之间加一层归一化,别名表管跨语言、模糊匹配管大小写
- 问题二:一次分析 60 秒,重复查询成本高
  - 解决:归一化 key 的内存缓存,62.70 秒 → 0.021 秒

### 第 8 页 · 工程质量
- 统一错误契约:`{"error": {"code", "message"}}`,四类错误代码
- 输入校验:空值与超长输入在调用 LLM 前拦截
- 6 条手动测试用例全部实测通过 + 4 项安全自查逐条验证

### 第 9 页 · 收获与展望
- 收获:从零搭起一条 LLM 应用的完整链路;理解 agent 的本质是让 LLM 做决策、代码做执行;体会到工程质量(错误契约、缓存、测试)决定原型能否交付
- 展望:支持多条独立 claim;缓存持久化;引入向量检索做粗筛以降低 LLM 调用量

## 3 分钟演示讲稿

**开场**

这个项目解决一个问题:手上有一个专利,想知道某家公司的哪些产品可能侵权。人工做要逐条读权利要求再对照产品说明,很慢。我做的这个工具把初筛这一步自动化——输入专利号和公司名,它返回最可能侵权的两个产品和判断理由。

**现场演示**

我现在输入标准用例:专利号 US-RE49889-E1,这是一个关于"点击广告后自动跳转并加入购物清单"的专利;公司填 Walmart。

点击分析。后台会做这几件事:找出这个专利的第一条独立权利要求,用大模型从中提取关键技术特征,然后拿这组特征给 Walmart 的 10 个产品逐个打分,最后取分数最高的两个。一次完整分析大约 60 秒,内部有 11 次大模型调用。

**讲解结果**

结果出来了。最上面是整体风险评估,三句话说明这家公司的整体侵权风险处于什么水平。

下面是两张产品卡片。第一个是 Walmart Shopping App,风险等级 Moderate,橙色徽章。它命中了"展示产品电子广告"和"将产品标识添加至在线购物清单"这两条特征,下面是模型给出的判定理由——它同时指出了哪些特征没有对上,所以判为部分吻合而不是高度吻合。

这两个产品都是 Walmart 购物清单和广告相关的核心应用,和人的直觉是一致的,说明筛选是有效的。

**收尾**

如果我再查一次同样的组合,会瞬间返回,因为加了缓存——实测从 62 秒降到 0.02 秒。

这个项目对我来说最大的收获有两点:一是完整走了一遍 LLM 应用从数据、后端、前端到 agent 的链路;二是意识到让原型变成能交付的东西,靠的不是新功能,而是统一的错误处理、输入校验、缓存和真实跑过的测试。
