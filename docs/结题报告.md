# 「专利侵权风险初筛」项目结题报告

## 项目目标

给定一个专利和一家公司,自动筛出该公司最可能构成侵权的产品,并说明判断依据。目标不是替代法律判断,而是把一家公司几十个产品缩小到最值得人工细看的两三个,把初筛这一步从人工阅读变成可自动化的流程。

## 系统架构

系统分为四层:React 前端负责输入与结果展示;FastAPI 后端提供 REST 接口并承载分析流水线;LangChain 封装对 Gemini 的调用;数据层为本地 JSON 文件。

一次分析的内部流程是:按专利号和公司名查出记录 → 解析 claims 并定位第一条独立权利要求 → 用 LLM 提取 3~6 条技术特征 → 拿这组特征逐个给公司产品打分 → 按分数排序取 Top 2 并映射为风险等级 → 再调一次 LLM 生成整体风险评估。后端按职责拆成六个模块,每个模块只做一件事,便于单独测试和替换。

## 关键技术点

**claims 解析。** 专利权利要求文本冗长且互相引用。通过判断文本中是否出现 "of claim"、"according to claim" 来区分独立与从属权利要求,只对独立 claim 做分析以控制成本。特征提取由 LLM 完成,prompt 要求只输出 JSON 数组;针对模型习惯性给 JSON 套代码围栏的问题,加了清洗和一次重试兜底。

**LLM 打分。** 把专利特征和产品描述一起送入 prompt,要求返回 `{score, matched_features, reason}`。关键在于 prompt 里写明评分标准(80-100 高度吻合、40-79 部分吻合、0-39 基本无关),否则模型给出的分数会全部挤在中间段,失去区分度。

**agent 路由。** 把三项已有能力封装成工具函数,由 LLM 判断用户的自然语言问题该调用哪个工具、并抽取参数。路由模型只输出一个 JSON,程序按 `tool` 字段分发;当参数缺失时,LLM 将缺失项列入 `missing`,程序据此反问用户而不是报错。温度设为 0 保证同样的问题得到同样的路由判断。

## 标准用例结果

以 `US-RE49889-E1`(广告点击跳转购物清单)× Walmart 为标准用例:系统从 10 个产品中选出 Walmart Shopping App 和 Walmart Grocery,风险等级 Moderate,命中"展示产品电子广告""将产品标识添加至在线购物清单"等特征。这两个产品确实是该公司购物清单与广告相关的核心应用,与人工直觉一致。

同一用例在不同公司上也验证过通用性:模块对软件类和机械类专利都能正常提取特征并打分。

## 三个难题与解决

**一、区分"无匹配"与"系统故障"。** 早期实现中,LLM 调用失败的产品被记为 0 分放进结果,导致服务整体不可用时返回的仍是一组 0 分产品,与"这些产品确实无关"的正常结论无法区分。改为失败调用直接跳过、不进结果集,空结果集就成为"全部失败"的可靠信号,503 判断随之准确。

**二、跨语言的公司名匹配。** 用户输入"沃尔玛",数据中存的是 "Walmart Inc.",子串模糊匹配对跨语言无能为力。解决方式不是在 agent 里写翻译逻辑,而是在 agent 与数据层之间加一层公司名归一化:别名表负责中文名与简称,原有模糊匹配负责大小写与不完整输入,两层各司其职,上层调用者无需关心名字怎么写。

**三、重复查询的成本。** 一次完整分析要调 11 次 LLM,耗时约 60 秒。加入以归一化后的 `(专利号, 公司名)` 为 key 的内存缓存后,相同查询实测从 62.70 秒降到 0.021 秒。归一化是关键——若不统一大小写,`Walmart` 与 `walmart` 会各存一份,缓存形同虚设。

## 不足与下一步

当前只分析每个专利的第一条独立权利要求,未覆盖从属权利要求,判断维度偏窄;缓存是进程内的,服务重启即失效;公司别名表靠手工维护,扩展性有限;数据为固定样本库,非实时检索。

下一步可考虑:支持多条独立 claim 的并行分析并汇总;把缓存换成文件或 Redis 以跨重启保留;引入向量检索先做一轮粗筛,减少需要 LLM 打分的产品数量,从而降低耗时与成本。
